## 主理人裁决摘要（2026-11-16）

1. **EXE 方案**：采用 PyInstaller `--onefile --noconsole` 作为构建期工具，不视为运行时第三方依赖，故不违反「零第三方依赖」政策；动手前必须先做 ≤150 行改动的 POC 冒烟（未装 Python 的干净环境启动、耗时、体积、杀软误报、长路径与 ADS 复验）。POC 不达标则改走 Python Embeddable + 启动器过渡形态。Nuitka onefile 仅作备选。**拒绝为原生 GUI 引入第三方依赖。**
2. **当前状态必须诚实披露**：理巢目前仍依赖本机 Python，`start_nesttidy.bat` 是启动脚本不是交付物。在 EXE 落地并验收前，任何公开文案不得写「免安装 / 开箱即用 / 双击即运行」。
3. **文档归位**：公开简介写进既有 `README.md` 第 1 节；分级计划写进既有 `ROADMAP.md` 第八节；治理文档合计保持 ≤600 行。
4. **来源纪律**：下表所有非理巢事实都带来源与访问日期；查不到写「未查证」。厂商自述数据明确标注「厂商口径」。

## 2. 逐款「值得借鉴的设计」与底线判定

**判定口径**：符合＝可直接纳入理巢且不触碰底线；需裁剪＝只取思路、去掉联网/安装/语义/删除等属性；直接排除＝与「离线、单人、不安装、不删文件、不判语义、不追求大而全」任一底线正面冲突。

### 1) BleachBit
- **① Preview 与 Delete 双按钮物理分离** → **符合**。理巢已有「预览只读 + 计划与执行分离」，可借鉴其按钮级隔离的可视强度，把预览结果做成独立的、不可误触的执行入口。
- **② CleanerML 声明式可编辑规则** → **需裁剪**。规则灵活性值得学习，但理巢规则版本 P0-R0-R5-v3 已冻结、九条不变量依赖固定规则集；开放规则编辑等于放弃冻结保证。
- 附：文件粉碎、隐私擦除、注册表清理 → **直接排除**（理巢不删除文件）。

### 2) czkawka / Krokiet
- **① 空文件夹「高级算法」处理嵌套空目录** → **符合**。与 R0 空目录清理同构，可用来复核 R0 对「空套空」的边界行为是否完整（当前实现细节【需核实】）。
- **② 在仓库/README 中把「无网络、无遥测、无统计」写成可核查承诺** → **符合**。理巢事实已满足，只差公开表述；可在既有 README 中补一句可核查声明，零成本对齐底线。
- 附：三级哈希 + 缓存 + 相似媒体 → **直接排除**（理巢不比较内容、不做重复判定、不做缓存状态文件）。

### 3) dupeGuru
- **① 参考目录 + 每组至少保留一个的保护机制** → **需裁剪**。保护意图与理巢「不静默覆盖、不跨资源根」同源，但「参考目录」是新增配置概念，理巢无删除动作，引入它只会增加无关设置面。
- **② 官方主动警告模糊匹配会产生误报并要求人工复核** → **需裁剪**。理巢按底线不判语义、不做模糊匹配；可借鉴「工具主动声明判定边界」的表达方式，写进报告页脚而非引入新规则。
- 附：图片两两比较 O(n²) 的性能陷阱 → 作为反例：理巢应避免任何两两比对类算法。

### 4) WizTree
- **① 直读 MFT 的吞吐优化思路** → **需裁剪**。速度目标值得学，但 MFT 直读需管理员权限、与「点击即运行、不弹提权」冲突；理巢应只取「减少重复元数据读取」的思路，不引入 MFT 依赖。
- **② 正确处理硬链接、不重复计数** → **需裁剪**。理巢只做路径结构整理、不做容量统计，该准确性指标不适用；但「对文件系统特殊结构保持谨慎」的态度可转化为长路径/ADS 已有实测项的持续覆盖。
- 附：`46x faster` 为厂商口径，不建议写进理巢任何对外文案。

### 5) TreeSize Free
- **① 结果按大小排序 + 树/图双视图** → **需裁剪**。理巢不做空间分析；只取「结果必须可排序、可下钻」的交互原则，用于提升报告可读性。
- **② 便携版分发** → **符合**。形态目标一致。
- 附：匿名使用数据收集（即使可关）→ **直接排除**。理巢底线是「无任何联网代码」，不是「默认关闭联网」。

### 6) CCleaner
- **① 清晰的 Free/Pro 能力对照表与版本变更日志** → **需裁剪**。可借鉴「变更可追溯」的表达，但只能写入既有 README，不得新增第三份产品文档。
- **② 一键清理 / 自动调度 / 云盘清理 / 驱动更新** → **直接排除**。联网、账号、云、后台服务、大而全套件，五项全踩底线，不作任何借鉴。
- 附：其安装器 + WebView2 依赖正是理巢必须避开的反面形态。

### 7) jdupes
- **① 「数据丢失避免为最高优先级，谨慎路径永远优先」的工程价值观** → **符合**。与理巢九条不变量完全同频；可写进 README 作为设计原则陈述（不需改代码）。
- **② 危险选项需输入两次才生效 / 文件变更检查防 TOCTOU** → **需裁剪**。理巢无危险选项、已有计划/执行分离与执行前复核，再加一层确认会降低「点击即运行」的顺畅度；保留其「不可逆动作必须显式」的思想即可。
- 附：哈希后逐字节校验 → **直接排除**（理巢不比对文件内容）。

### 8) Kondo
- **① dry-run 作为一等公民（v0.9 新增）** → **符合**。与理巢「预览只读 + 冻结计划」同构，可作为报告页「先看后做」交互的参照。
- **② 按项目类型语义识别清理目标** → **直接排除**。理巢明确「不判断目录名语义」，且 Kondo 是永久删除，双重冲突。
- 附：其 README 的大号 Warning + 备份建议 → **需裁剪**：可保留一句风险提示，但不应把备份流程变成产品职责。

### 9) rem_stubs
- **① 极小单用途 C 工具，只做「删空目录」一件事** → **符合**（定位层面）。与理巢「只做一件事」高度一致，是范围克制的正面样本。
- **② 需自行编译、无预编译 EXE、递归仍在 Planned** → **直接排除**（交付形态层面）。它恰好反衬理巢已完成 R0 递归与只读预览，也提醒我们：功能再小，只要不能双击运行就不达标。

### 明确排除的方案清单（汇总）
联网/云同步/账号/协作/遥测/更新检查；语义猜目录；自动删重复；数字后缀撞名；安装器/NSIS/商店分发/后台服务/计划任务；MFT 直读、树图、注册表清理、驱动更新等大而全套件；规则引擎开放编辑/插件系统；跨平台宣传。

## 3. 理巢当前不足（严格分层，不混写）

### 【实测】（2026-11 Windows 实机数据）
1. **免安装/开箱即用差距（核心不足）**：完成 10 万文件全流程仍需本机安装 Python 3.11+，`start_nesttidy.bat` 只是启动脚本，不是可点击即运行的交付物；EXE 尚未封装。这直接违反「无需安装、开箱即用，即使封装 EXE 也必须点击即运行」的底线。
2. **性能边界**：10 万文件生成 380.158s、规划 342.692s（插桩 358.516s），合计约 12 分钟量级；插桩带来约 15.8s 额外开销。对「单资源包整理」的常见交互式场景，等待感知可能偏重。峰值内存 109.54 MB 属可控范围，非主要矛盾。
3. **安全边界已验证但覆盖有限**：P0 越界 0、长路径通过、ADS Zone.Identifier 由 `shutil.copy2` 保真（判定为预期行为非缺陷）均已实测；**管理员提权场景未验证**，这是一个明确的事实缺口。

### 【推断】（基于对比与产品逻辑，未实测）
1. **操作体验**：本地 Web UI + 浏览器形态，对「双击 → 选目录 → 看结果 → 执行」的短链路而言，浏览器窗口/端口概念可能是多余认知负担；竞品（BleachBit、WizTree）均提供原生窗口。此推断需用户测试确认，不应直接推导为「改原生 GUI」——那会引入第三方依赖，违反底线。

## 4. 升级计划（三档，含取舍理由）

### A. 近期必做（P0）

**A1. EXE 单文件点击即运行（最高优先级）**
- **做什么**：把 `start_nesttidy.bat` 的启动链封装为单个 `nesttidy.exe`，双击后在 `127.0.0.1:8766` 打开本地界面；EXE 内嵌 `longPathAware` manifest；保持 Python 3.11+ 标准库实现与零第三方运行时依赖不变。
- **路径选择与风险（带依据的推荐）**：
  - **推荐：PyInstaller `--onefile --noconsole`（构建期工具）**。依据：理巢已是纯标准库 Python + 内联 HTML + 入口脚本形态，PyInstaller 对此类项目改造面最小；构建期引入工具 ≠ 运行时引入第三方依赖，因此不触碰「零第三方依赖」政策。风险：① 体积（纯标准库 onefile 通常仍达十余 MB 量级，具体值需实测，不臆测）；② 首次启动需解压到临时目录，启动速度慢于直接 Python；③ 杀软误报可能；④ 需重新验证长路径、ADS 保真与多线程不变量在打包形态下的行为。**主理人已裁决采用此路径，但须先完成 POC 冒烟。**
  - **备选 B：Nuitka `--onefile`**。启动通常更快，但需 C 工具链、构建链更重，且内联 HTML/动态导入需额外验证；仅在 PyInstaller 启动时间不可接受时再评估。
  - **备选 C：Python Embeddable Package + 启动器**。免安装但为多文件目录，不满足「单文件 EXE」要求，只可作过渡，不推荐。
  - **不推荐**：为做原生 GUI 引入 PyQt/Tk 之外的第三方框架，或引入打包后仍需额外 DLL/文件夹的方案。
- **为什么不突破底线**：全本地运行、无联网、无安装器、无账号；双击即运行；规则版本与九条不变量不变；零第三方运行时依赖不变。
- **验收口径**：① 冒烟：在未安装 Python 的干净 Windows 10/11 环境，仅拷贝 1 个 EXE，双击能打开界面并完成小样本整理；② 里程碑：同环境跑通 10 万文件口径，`mappings=operations=100000`、P0 越界 0、长路径通过，实测内存峰值与启动耗时记录为新基线；③ 68 例测试全通过；④ 防火墙规则下确认零出站连接。
- **取舍理由**：用「体积 + 首次启动数秒」换取底线达标，收益远大于成本；这是唯一不改产品定位的路径。

**A2. 报告可读性增强（仅展示层）**
- **做什么**：在现有预览/结果页增加按 R0–R5 的分类计数、R5 撞名前缀样例前 N 条、`P0 越界 0` 显式提示、`operations / mappings` 摘要。
- **为什么不突破底线**：不改计划语义、不改规则、不删文件、不新增产品文档文件。
- **验收口径**：10 万文件实测中，一屏可见总数、各规则计数、R5 样例；展示层改动前后 `mappings/operations/P0` 逐项一致。
- **取舍理由**：竞品普遍具备可复核的结果面板；这是低成本、高感知收益，且完全不动冻结规则。

**A3. README 补一段可核查的本地化声明**
- **做什么**：在既有 README（不新增第三份产品文档）写明：无联网代码、Web 仅绑 127.0.0.1、不删除文件、重复文件只报告、规则版本 P0-R0-R5-v3。
- **为什么不突破底线**：纯文字说明，不引入功能；与竞品 czkawka 的可核查承诺做法一致。
- **验收口径**：声明逐条能在源码与实测口径中找到对应证据（grep + 防火墙验证）。
- **取舍理由**：零成本把已有事实变成用户可验证的承诺。

### B. 后续优化（P1）

**B1. 性能剖析与行为保持型优化**
- **做什么**：定位 380.158s 生成 / 342.692s 规划的热点，优先减少重复元数据读取；插桩开销（约 15.8s）单独计量。多线程优化必须以「结果不变」为前提。
- **为什么不突破底线**：只优化实现，不改规则、不引入缓存数据库/索引等状态文件。
- **验收口径**：优化前后输出逐条比对一致（mappings/operations/P0 越界 0）；耗时与内存峰值给出前后对照；68 例测试通过。
- **取舍理由**：规则已冻结，性能只能在实现层挖掘；引入索引会破坏「单工具、无状态、开箱即用」。

**B2. 操作体验细节 + 事实缺口补齐**
- **做什么**：明确端口占用时的用户提示；补齐管理员提权场景验证；把长路径与 ADS 的既有结论写成用户可理解的帮助文本（写入既有手册，不新增文档）。
- **为什么不突破底线**：仅提示与验证，不新增后台服务、不弹权限请求作为常规路径。
- **验收口径**：端口占用场景有明确可读提示；管理员场景有「已验证/未验证」的明确结论。
- **取舍理由**：先消除不确定性，再谈交互改版；避免把浏览器形态误改成原生 GUI 而引入依赖。

**B3. 最小化本地配置**
- **做什么**：若当前尚不可配，仅补「目标资源根路径」与「服务端口」两类本地参数（存本机、不联网）。**不开放规则阈值、语义开关、排除规则编辑器**。
- **为什么不突破底线**：配置面不触及规则版本与九条不变量；无账号、无同步。
- **验收口径**：规则版本仍为 P0-R0-R5-v3；配置仅落在本机；68 例测试通过。
- **取舍理由**：只补用户表达意图的最小通道，拒绝配置面板膨胀。

## 9. P0 推进结果（2026-11-17）

### 9.1 端口占用提示修复（已落地）

- 问题：`web.py:serve()` 无异常分类，端口占用时抛裸 OSError；`start_nesttidy.bat` 只打印「请确认已安装 Python」，误导。
