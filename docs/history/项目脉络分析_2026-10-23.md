# 文件整理项目 · 版本存档脉络分析

**【现行】** 规范与路线的事实依据。结论已被 `AGENTS.md`、`ROADMAP.md` 采用。

> 分析对象：项目资产「文件整理项目版本存档.zip」（3.4 MB，21 个版本目录 + 20 个散落文件）
> 分析日期：2026-10-23
> 数据来源：存档内代码/文档原文 + 本地实测（Python 3.13.12 / Windows）

---

## 一、一句话结论

这不是「一个工具迭代了 11 版」，而是**一个规则内核（剥壳 + 提级 + 溯源改名）被两代产品形态、三种架构反复重写了 20 次**。规则本身六个月没变，变的是**边界定义**和**代码组织方式**；最后一次交付（2026-05-14，v0.4.0）是唯一一版「需求→规则→实现→审计」闭环齐全的产物，之后停摆约 5 个月。

## 四、真正稳定的东西：规则内核

20 次重写里，**核心规则只改过两次**，都在「边界」上：

| 规则 | 2025 雏形 | V5~V11 表述 | Ver3.00 表述 | v0.4.0（现行） |
|---|---|---|---|---|
| 空目录 | 删 | 倒序空目录清理 | R0 前置清理 | R0 前置清理 |
| 剥壳 | 穿透（0 文件 + 1 子目录 → 撕掉） | 「穿透」/「智能解包」 | **R1 直链穿透（仅根层级）** | **R1 资源根内直链穿透** |
| 单壳吸收 | — | — | R2 壳吸收（保留外层名） | R2 同名（保留外层名） |
| 分叉口 | 全提 / 全留 | 同生共死 | R3（根强制全留 + 冻结） | R3（**父级保护**，可深入整理） |
| 单文件提级 | 提 | 单级提级 | R4（未冻结才提） | R4（不跨资源根） |
| 撞名 | 「前身前缀」 | 数字后缀 `_1` ⚠️ | R5 溯源前缀 | R5 基于 `original_path` |
| **边界** | 无 | 无 | 「根 = 所选目录」 | **P0：运行根 ≠ 资源根** |

三个关键修正点，每一个都对应一次真实的失败：

1. **「同生共死」→「父级保护」**：早期把分支整体冻结，导致 `A/外壳/正文/file.txt` 永远理不干净；改成「父级不许打散它，但它内部照常整理」。
2. **数字后缀 → 溯源前缀**：V2/V3 手册写的是 `file (1).txt`、`_from_原目录名`，与用户「绝不使用 (1)(2) 无意义后缀」的原始要求直接矛盾。这条在 V5.3 手册里被写错，直到 Ver2.0《需求再澄清》才纠回来。
3. **P0 运行根保护**：这是整个项目的转折点。Ver3.00 把「用户所选目录」当根，R1 允许一路穿透到根——正是用户抱怨的「我要的是 `资源包\xxx\`，你给我提到了 `资源包\`」。v0.4.0 引入「运行根只是容器 / 第一层子目录才是整理对象 / 文件最高只能提到资源根内」。

## 五、三次架构摆动，驱动力各不相同

```
单文件 62KB ──功能膨胀──▶ 单文件 138KB (V8)
                              │
                    可维护性崩溃 ▼
           20 模块 (V9/V10, 9.9k 行)
                              │
                    维护成本反噬 ▼
      精简 8 模块 (Ver3.00, 2.6k 行) ──▶ 交付 6 模块 (0.4.0, 1.9k 行)
```

- **第一次拆模块（V7.5→V9）**：单文件已到 138 KB，改一处要通读全文。动机是工程正确。
- **第二次重组（V9→V10）**：模块命名混乱（数字 vs 中文），审查报告指出接口不清。动机是规范。
- **第三次收缩（V10→Ver3.00→v0.4.0）**：10k 行、20 模块、6 大引擎，**但用户真正要的只有一件事**——把资源包里的空壳剥掉。于是砍到 1.9k 行、6 个模块。动机是**回归产品本质**。

这次收缩是有代价的：V11 手册里那 11 项「回移植」功能（交互式预览、`--only-restructure`、硬链接去重、离线分析、Zone 精细控制）在 v0.4.0 里大部分只保留了降级版（去重只报告不硬链接、离线分析缺失）。

## 六、最新交付（v0.4.0）的真实状态

### 我实测的结果

```
python -m unittest discover -s tests
Ran 14 tests in 6.770s
FAILED (failures=1)   ← test_name_cleaning_then_conflict
```

**根因不是算法缺陷**，是测试夹具本身在 Windows 上无效：

```
A/CON.txt  →  Path.exists() = True，但 is_file() = False，目录列表为空
              （CON 是 Windows 控制台设备名，写进去的是设备不是文件）
```

`build_tree()` 把它归入 `SKIPPED_SPECIAL` 跳过，映射表里自然没有它，于是断言失败。**但这件事本身就说明：这套规则从未在 Windows 上做过真实回归。** Ver3.00 的 PROJECT.md 也白纸黑字写着「所有测试在 Linux 上通过，Windows 文件系统行为需实机确认」。

### 已实现 vs 已声明

| 手册/审计声明 | 实际代码 | 判定 |
|---|---|---|
| P0 批量边界保护 | `planner.resource_roots()` + `IGNORED_ROOT_FILE` | ✅ 有测试 |
| R0–R5 六规则 | `rules.py` 243 行，含 `stable_key` 确定性排序 | ✅ 有测试 |
| R5 基于原始路径 | `prefixed_name(entry.original_path, ...)` | ✅ 符合手册 13.5 |
| 文件名清洗 | `clean_name()`：非法字符/保留名/尾随点/180 字符截断 | ✅ 逻辑完整 |

| move 事务日志 | `transaction_log.jsonl` + `undo` 命令 | ✅ 但 rmdir 不重建 |
| 百万级支持 | Web 只显示前 500 条，历史进 SQLite | ⚠️ 规则计划仍全内存，未做分页虚拟化 |
| 管理员提权 | `--no-elevate` 可关，但无提权子进程 | ⚠️ 审计自己承认未实现 |

## 七、未闭环的风险（按重要性）

1. **Windows 规则回归缺失（高）**：所有规则验证都在 POSIX 语义下完成。大小写不敏感、ADS、盘符、259 字符截断、保留设备名——全是 Windows 特有的坑，一个都没实测过。
2. **文档漂移（中）**：同一规则存在 4 套表述（V2 手册 / V5.3 手册 / Ver3.00 `文件清理规则.md` / 理巢手册 v1.0），其中 V5.3 手册的「数字后缀」与最终要求相反。后来者读错文档就会写错代码。
3. **V11 需求悬空（中）**：V11 只有手册无代码，11 项回移植需求处于「说过但没做、也没正式废弃」的悬空态。
4. **性能承诺未验证（中）**：手册承诺 ≤100 万文件，实测基准是 16 万节点离线分析，不是真实磁盘扫描+计划生成。
5. **撤销不完整（低）**：`undo` 只回滚 move，空目录删除不重建。

## 八、判断与建议

**判断**：项目不缺功能，缺的是「在当前平台上把已有规则钉死」。继续沿 V11 路线做全功能回移植是重复 4 月的错误——那次膨胀到 10k 行 20 模块，最后还是被推翻。

**建议的下一步（按优先级）**：

1. **建立 Windows 回归基线**：把 14 个用例改写为跨平台安全夹具（禁用 `CON/PRN/AUX/NUL/COM1` 等设备名做文件名），补 5 类 Windows 专有场景：大小写同名、`\\?\` 长路径、ADS Zone.Identifier、保留设备名清洗、中文路径截断。
2. **规则文档单一化**：以《理巢_产品开发手册 v1.0》第 4 章为唯一权威，其余三套标注「历史版本，已被取代」，避免继续写错。
3. **补 P0 × R1 交互用例**：这是历史上唯一反复出问题的接缝（运行根散落文件 + 单壳链并存、资源根内多壳并联、单资源模式下选中目录本身是壳）。
4. **V11 需求做一次性裁决**：逐项标注「保留 / 放弃 / 降级」，不要留悬空。
5. 性能与大规模分页留到规则正确之后，不要先优化。
