## 1. 产品名称与定位

产品名称统一为：**理巢**。

理巢是一款面向个人资源整理场景的本地文件清理工具，核心目标是：

> 清理资源包内部冗余的嵌套空壳目录，将深层文件提升到合理层级，输出干净、扁平、语义清晰的目录树。

产品不是通用文件管理器，也不是自动语义分类工具。它的核心价值是：

- 清理下载、网盘、BT、压缩包解压后常见的多层无意义包装目录。
- 保留用户认为有意义的资源项边界。
- 在不做目录名语义判断的前提下，通过确定性结构规则完成整理。
- 尽量保证数据安全、执行可预览、可追踪、可恢复。

---

## 2. 最关键的需求澄清：运行根目录不是整理目标

讨论中最重要的规则修正是区分两个概念：

### 2.1 运行根目录

用户选择执行清理的目录，例如：

```text
D:\下载\资源包\
```

它只是算法边界和容器，不是整理结果的承载层。

运行根目录本身不参与提级、剥壳、合并。运行根目录下原本已有的文件也不处理、不移动、不重命名，直接忽略。

### 2.2 资源根目录

运行根目录下的每个直接子文件夹，例如：

```text
D:\下载\资源包\电影A\
D:\下载\资源包\课程B\
D:\下载\资源包\资料C\
```

这些才是实际整理对象。

资源根目录的名称默认有意义，必须保留。任何规则都不得把文件提升到运行根目录下。

例如：

```text
资源包\
  说明.txt
  电影A\
    正片\
      movie.mkv
```

整理后应为：

```text
资源包\
  说明.txt
  电影A\
    movie.mkv
```

而不是：

```text
资源包\
  说明.txt
  movie.mkv
```

## 3. 支持两种入口模式

后来从产品经理视角补充了一个重要需求：实际使用中，用户不一定选择资源包父目录，也可能直接选择某个资源目录。

因此产品需要支持两种模式：

### 3.1 批量模式

用户选择的是资源包父目录。

```text
资源包\
  电影A\
  课程B\
  软件C\
```

此时：

- 所选目录 = 运行根目录。
- 所选目录的直接子文件夹 = 资源根目录。
- 所选目录里的散落文件不处理。
- 文件最高只能提升到各自资源根目录内。

### 3.2 单资源模式

用户直接选择某个资源目录。

```text
电影A\
  正片\
    movie.mkv
```

此时：

- 所选目录本身 = 资源根目录。
- 所选目录名保留。
- 文件最高只能提升到该目录内部。
- 不得提升到它的父目录。

UI 中应明确让用户选择模式，或者自动建议但不要静默强制。

## 4. 核心整理规则的最终意图

核心算法采用确定性结构规则，不依赖 AI 或目录名语义判断。

### P0：运行根保护

运行根目录不参与整理。运行根目录中的原始文件不处理。运行根目录的直接子文件夹视为资源根目录。

在单资源模式下，用户选择的目录本身就是资源根目录。

### R0：空目录删除

空目录直接删除。

这是明确产品策略，不保留空目录。

### R1：资源根内直链穿透

如果某个资源根目录内部只有一条连续嵌套链，例如：

```text
电影A\
  外壳1\
    外壳2\
      正文\
        movie.mkv
        poster.jpg
```

整理为：

```text
电影A\
  movie.mkv
  poster.jpg
```

注意：

- 保留资源根目录 `电影A`。
- 删除其内部的包装链。
- 终止点目录也删除，因为内部目录名不一定可靠。
- R1 命中后，该资源根目录停止后续结构整理。

该决策源于一个原则：第一层资源目录名可信，内部目录名不可信。

### R2：壳吸收

壳目录定义为：

```text
0 个文件 + 恰好 1 个子文件夹
```

R2 的行为是保留外层目录名，吸收内层目录内容。

例如：

```text
资料A\
  A\
    B\
      file.txt
```

处理后为：

```text
资料A\
  A\
    file.txt
```

而不是：

```text
资料A\
  B\
    file.txt
```

理由：程序不做名字语义判断；外层名字优先保留。

### R3：分叉口判定

分叉口定义为：

```text
0 个文件 + 2 个及以上子文件夹
```

非根分叉口分两种情况：

#### 全提

如果所有直接子文件夹都恰好只有 1 个文件且没有子文件夹，则全部提级。

```text
合集\
  A\
    a.txt
  B\
    b.txt
```

整理为：

```text
合集\
  a.txt
  b.txt
```

#### 全留 + 父级保护

如果至少一个子文件夹包含多个文件，或仍包含子文件夹，则保留所有直接子文件夹边界。

```text
合集\
  A\
    file.txt
  B\
    b1.txt
    b2.txt
```

保持为：

```text
合集\
  A\
    file.txt
  B\
    b1.txt
    b2.txt
```

其中 `A` 不应被父级继续提级到 `合集` 下。

### 重要修正：冻结不是冻结整棵子树

讨论中明确：所谓“冻结”应改为“父级保护”。

父级保护的含义是：

- 父目录不得把该子目录的内容提到父级层。
- 父目录不得删除该子目录边界。
- 但进入该子目录内部后，它仍然可以正常执行 R0-R4。

例如：

```text
合集\
  A\
    外壳\
      正文\
        file.txt
  B\
    b1.txt
    b2.txt
```

整理后应为：

```text
合集\
  A\
    file.txt
  B\
    b1.txt
    b2.txt
```

而不是保留 `A\外壳\正文\file.txt`，也不是把 `file.txt` 提到 `合集` 下。

### R4：单文件提级

递归处理完成后，如果当前节点下某个未受父级保护的直接子文件夹只有一个文件且无子文件夹，则将该文件提到当前层，并删除该子文件夹。

但 R4 不得跨越资源根边界。

允许：

```text
电影A\
  正片\
    movie.mkv
```

变成：

```text
电影A\
  movie.mkv
```

不允许：

```text
资源包\
  电影A\
    movie.mkv
```

变成：

```text
资源包\
  movie.mkv
```

### R5：重名冲突解决

发生同名冲突时，所有冲突方都改名，不使用数字后缀。

基本策略：从原始来源路径中逐级向上追加祖先目录名前缀，直到当前层无冲突。

例如：

```text
合集\
  A\
    cover.jpg
  B\
    cover.jpg
```

提级后应命名为：

```text
合集\
  A-cover.jpg
  B-cover.jpg
```

若仍冲突，则继续向上追溯：

```text
Group1-A-cover.jpg
Group2-A-cover.jpg
```

实现时必须记录原始路径，不能只依赖移动后的当前路径。

## 5. 产品策略决策

本次对话中明确了以下产品策略：

1. 空目录删除。
2. 默认进入试运行模式。
3. 正式执行支持 copy 和 move 两种模式。
4. 选择 move 时必须弹出风险提示并要求确认。
5. 系统文件、系统隐藏文件、符号链接等排除。
6. 普通隐藏文件正常处理，因为有些隐藏属性是异常权限或错误标记造成的。
7. 权限修复默认关闭，并提供可勾选的具体修复项。
8. 支持重复文件检查，但默认只报告，不自动删除。
9. 支持文件名非法字符清洗。
10. 不联网运行；如缺少运行必要组件，应明确提示。
11. 默认请求权限提升，以管理员权限运行，尽量减少权限失败。

## 6. 执行安全与异常处理

产品最重要的非功能目标是数据稳定性。

### 6.1 默认试运行

所有真实执行前必须先生成执行计划和预览。

预览应展示：

- 原路径。
- 目标路径。
- 触发规则。
- 是否发生重命名。
- 是否发生文件名清洗。
- 风险等级。

### 6.2 copy 与 move

copy 模式：

- 源目录不变。
- 必须选择输出目录。
- 输出目录不得位于源运行根内部。
- 执行前检查目标盘空间。

move 模式：

- 会修改源目录。
- 必须二次确认。
- 必须写入事务日志。
- 应支持失败恢复和尽力撤销。

### 6.3 异常自救修复

权限修复默认关闭，但执行过程中如果某个计划项因权限、只读、隐藏、Zone.Identifier、路径过长、非法文件名等导致无法操作，应执行最小必要的异常自救修复。

若自救后仍失败：

- 跳过该项。
- 在 UI 执行过程界面中显示。
- 写入操作记录。
- 添加特殊标记，供用户后续排查。

正常文件不需要逐条显示，只更新进度条和统计数字。

### 6.4 异常中心

UI 应只突出异常项，而不是刷屏显示所有成功项。

异常项应支持：

- 查看原因。
- 打开所在位置。
- 复制路径。
- 重试。
- 导出报告。

---

## 7. 权限修复与文件名清洗

### 7.1 主动权限修复

这是用户主动勾选的功能，默认关闭。

可修复项包括但不限于：

- 清除只读属性。
- 清除普通隐藏属性。
- 清除 Zone.Identifier ADS。
- 尝试修复当前用户访问权限。

系统文件、系统隐藏文件仍应排除。

### 7.2 异常自救修复

这是执行过程中为完成计划项而做的最小必要修复。它不同于主动批量权限修复。

### 7.3 文件名非法字符清洗

文件名清洗应发生在计划生成阶段，而不是执行失败后才临时补救。

计划中应记录：

- 原文件名。
- 清洗后文件名。
- 清洗原因。
- 是否触发二次冲突。
- 最终目标名。

---

## 8. 重复文件检查

重复文件检查是诊断功能，不是主流程的一部分。

默认关闭。用户启用后只生成报告，不自动删除、不自动移动、不自动合并。

建议分三档：

1. 快速检查：文件大小 + 文件名相似度。
2. 标准检查：文件大小 + 首尾分块哈希。
3. 深度检查：完整哈希。

深度检查可能非常耗时，尤其是大视频、压缩包、镜像文件。

## 9. 技术路线

最终确定的技术路线：

- Python 3.11+。
- 本地 Web UI。
- SQLite 存储扫描结果、执行计划、事务日志和操作历史。
- 不联网使用。
- 缺少必要运行组件时提示用户。

建议工程代码名可使用 ASCII 名称，避免中文包名和路径带来的开发问题。

---

## 10. 多线程与确定性

需要支持多线程以提高效率，但整理结果必须确定。

原则：

- 扫描可以并发。
- 哈希可以并发。
- copy 可以有限并发。
- 规则判定、目标路径生成、冲突解决必须基于排序后的稳定输入统一完成。
- 同一批文件多次试运行，输出计划应一致。

用户设置可简化为：

- 低占用。
- 自动。
- 高性能。

不要暴露太多底层线程参数。

---

## 11. 大规模处理目标

希望支持小于 100 万个文件系统条目。

这里的“条目”包括文件和文件夹。

建议能力分级：

- 0 - 10 万条目：标准模式。
- 10 万 - 50 万条目：大规模模式。
- 50 万 - 100 万条目：极限模式。
- 超过 100 万条目：允许尝试，但提示不保证体验。

中等偏上家用 PC 参考配置：

- CPU：6 核以上。
- 内存：16GB 以上。
- 磁盘：SSD。

大规模模式下应避免：

- 一次性加载完整树形 UI。
- 逐文件实时日志刷屏。
- 默认完整哈希。
- 一次性把全部映射加载进前端内存。

应使用：

- SQLite。
- 分页表格。
- 虚拟化列表。
- 统计摘要。
- 异常优先展示。

## 12. UI 与用户路径

主流程应是：

```text
选择目录
→ 选择模式：批量 / 单资源
→ 扫描
→ 生成计划
→ 预览
→ 用户确认
→ copy 或 move 执行
→ 进度与异常中心
→ 报告与历史
```

推荐预设：

1. 安全预览：只扫描和生成计划。
2. 安全复制：copy 到输出目录，源目录不变。
3. 标准整理：move 原地整理，二次确认。
4. 深度诊断：不整理，只做重复、权限、非法文件名、异常检测。

## 13. 必须特别注意的实现细节

### 13.1 不做目录名语义判断

不要试图判断 `电影A`、`正文`、`课程名称`、`新建文件夹` 哪个更有意义。

本产品依赖结构规则，不依赖语义猜测。

### 13.2 第一层资源名必须保留

无论批量模式还是单资源模式，资源根目录名都必须保留。

### 13.3 不得跨越资源根边界提级

文件最高只能提升到资源根目录内部。

### 13.4 父级保护不能误实现成整棵子树冻结

父级保护只禁止父目录打散该子目录；该子目录内部仍可继续整理。

这是容易写错的关键点。

### 13.5 R5 必须基于原始路径

移动、提级、重命名之后仍要能追溯原始路径。否则冲突解决无法稳定。

### 13.6 move 必须有事务日志

任何原地修改都必须记录，避免中断后无法恢复。

### 13.7 正常项不刷屏，异常项突出

执行 UI 不应逐条显示所有成功文件。正常项只更新进度和统计；异常项才进入列表。

### 13.8 排除符号链接和系统文件

避免递归循环、破坏系统结构或误处理特殊对象。

普通隐藏文件不排除。

### 13.9 正在下载或写入的文件应跳过

应识别常见未完成下载文件，例如：

```text
.crdownload
.part
.!qB
.aria2
.tmp
.downloading
```

并可通过短时间内 size / mtime 是否变化来判断疑似正在写入。

## 14. 建议 MVP 顺序

### MVP 1：安全预览版

- 批量模式 / 单资源模式。
- 扫描。
- P0 + R0-R5。
- 文件名清洗计划。
- 冲突解决。
- 预览。
- 规则解释。
- 报告导出。

### MVP 2：安全 copy 版

- copy 输出目录。
- 空间检查。
- 执行进度。
- 异常中心。
- 事务日志。
- 失败项报告。

### MVP 3：受控 move 版

- 管理员权限请求。
- move 二次确认。
- 执行前快照复核。
- 中断恢复。
- 重试失败项。
- 尝试撤销上次操作。

### MVP 4：增强诊断版

- 主动权限修复。
- 重复文件检查。
- 深度哈希。
- 大规模模式。
- 多线程性能优化。
- 历史记录管理。

---

## 15. 不建议当前阶段实现的功能

为避免产品膨胀，暂不建议实现：

- 云盘同步。
- 联网插件。
- 账号系统。
- 复杂隐私合规。
- 目录名 AI 语义识别。
- 自动删除重复文件。
- 跨设备任务同步。
- 远程 Web UI。
- 多人权限体系。

---

## 16. 对 Codex 的执行建议

Codex 实际编程时，应优先实现确定性核心和安全执行框架。

优先保证：

1. 边界正确：不动运行根、不跨资源根提级。
2. 计划正确：先生成计划，再执行。
3. 结果稳定：多次运行同样输入应得到同样计划。
4. 可追踪：每个计划项都有来源、目标、规则、状态。
5. 可恢复：move 操作有事务日志。
6. UI 不刷屏：正常项进度化，异常项列表化。
7. 大规模可撑住：SQLite + 分页 + 虚拟化，不一次性塞满内存。

开发中如果手册和本文有冲突，以《理巢_产品开发手册_v1.0.md》为准。
