# 理巢 NestTidy

**【现行】** 产品说明。规则语义以 `docs/规则对照表.md` 为准，执行规范见 `AGENTS.md`，路线见 `ROADMAP.md`。

理巢是一个离线本地目录整理工具，用确定性结构规则清理资源目录内部多余嵌套壳目录。它默认只生成试运行计划，不直接修改磁盘。

## 双击运行

双击 `start_nesttidy.bat`，软件会在当前文件夹启动，并打开 `http://127.0.0.1:8765`。

## 命令行运行

```powershell
python -m nesttidy.app --host 127.0.0.1 --port 8765
```

浏览器打开 `http://127.0.0.1:8765`。

## 命令行生成计划

```powershell
python -m nesttidy.app plan "D:\下载\资源包" --mode batch --report-dir ".\理巢报告"
python -m nesttidy.app plan "D:\下载\资源包\电影A" --mode single --report-dir ".\理巢报告"
```

## 测试

```powershell
python -m unittest discover -s tests
```

27 个用例，Windows 上必须全绿。POSIX 通过不算通过——历史上两个只在 Windows 暴露的缺陷就是这么漏掉的。

## 项目结构

```
nesttidy/         源码 16 模块，1,660 行
  rules.py        结构变换纯逻辑（虚拟树，不写磁盘）
  planner.py      扫描 + 生成冻结的 OperationPlan（只读）
  executor.py     唯一执行磁盘结构变更的地方
  model.py        数据类
  web.py app.py   本地 UI 与 CLI 入口
tests/            27 个用例（3 个文件）
docs/
  理巢_产品开发手册_v1.0.md   产品范围与规则定义
  规则对照表.md               规则↔代码↔测试 三方对照
  history/                    历史文档，只读，不许引用
```

## 功能范围

MVP1–MVP4 的本地可用能力：

- 批量模式 / 单资源模式
- **P0 边界保护**：运行根不参与整理，文件最高只能提到资源根内
- R0–R5 计划生成
- Windows 文件名清洗计划
- 本地 Web UI，默认绑定 `127.0.0.1`
- copy 执行，源目录不变
- move 执行，要求显式确认，写入事务日志
- 报告导出：`summary.md`、`summary.json`、`mappings.csv`、`issues.csv`
- 主动权限修复：清除只读、普通隐藏、Zone.Identifier
- 重复文件诊断：三档，只报告不自动删除
- SQLite 操作历史
- PDF 操作手册

## 诊断命令

```powershell
python -m nesttidy.app duplicates "D:\下载\资源包" --level standard
python -m nesttidy.app repair "D:\下载\资源包" --clear-readonly --clear-zone-identifier
python -m nesttidy.app history
python -m nesttidy.app manual
```

## 常用操作

```bash
# 回到任意历史版本（只读查看）
git checkout v5.3

# 看「单文件 → 20 模块」到底改了什么
git diff v8.0 v9.0 --stat

# 看某版本的全部文件
git ls-tree -r --name-only v7.5

# 时间轴（按提交时间）
git log --graph --oneline --all --decorate

# 回到最新
git checkout main
```

> 切到历史版本后如需改动，先建分支：`git switch -c explore/v5.3 v5.3`。
> 直接 commit 会进入 detached HEAD，改动容易丢。

## 历史是怎么重建的

这些提交不是当年真实敲出来的——2026-05-27 项目以 zip 存档封存，没有版本控制。
2026-10-26 从存档重建了完整历史，方法如下，请据此判断每条提交的可靠性：

- 每个提交 = 该版本目录的**完整快照**，`git checkout <tag>` 得到当时的全部文件。
- 提交时间使用该版本的**诞生时间**（存档内最早文件时间戳），不是真实提交时间。
- 文件时间戳本身不可靠：多处存在复制覆盖（例如 v6.62 目录里混入了 v7.0 的代码，时间戳早于 v6.6）。**顺序按语义排，不按 mtime 排。**
- 排除内容：`__pycache__`、`.pytest_cache`、版本目录内的 zip 压缩副本、PyInstaller 编译产物、`history.sqlite`。
- 目录内并存的多个代码副本**按原样保留**，没有清理——那是真实状态，也是「没有版本控制」的代价。
- 提交说明里的判断来自 `docs/history/项目脉络分析_2026-10-23.md`（对全部 21 个版本存档的通读）与源码核对。
